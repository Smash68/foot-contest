# AGENTS.md

Instructions pour les agents de code (et les contributeurs) travaillant sur ce dépôt : commandes, vue d'ensemble de l'architecture et workflow. Le détail des conventions vit dans [`docs/`](docs/).

## Commands

L'app tourne sous Docker (voir ADR 011) — aucune dépendance locale à PHP/Composer requise, seulement Docker. `docker compose up -d app` démarre le container `app` (PHP 8.4 CLI + extensions) et sa dépendance `database` (PostgreSQL), et exécute `composer install` à chaque démarrage.

Un `Makefile` raccourcit les commandes ci-dessous (`make test`, `make stan`, `make cs-fix`, etc.) — `make help` liste les cibles disponibles. Les commandes `docker compose` complètes restent valides, le Makefile n'est qu'un alias.

```bash
# Démarrer l'environnement (app + base de données)
docker compose up -d app

# Run all tests
docker compose exec app vendor/bin/phpunit

# Run a single test file
docker compose exec app vendor/bin/phpunit tests/Competition/Domain/SingleEliminationBracketGeneratorTest.php

# Run a single test method
docker compose exec app vendor/bin/phpunit --filter testMethodName

# Couverture de tests (Xdebug désactivé par défaut pour un run rapide — voir ADR 016)
docker compose exec app composer test:coverage

# Analyse statique (PHPStan niveau max — voir ADR 018)
docker compose exec app composer stan

# Style de code (PHP-CS-Fixer @Symfony — voir ADR 019)
docker compose exec app composer cs-check   # vérifie seulement
docker compose exec app composer cs-fix     # applique

# Console Symfony (ex: migrations)
docker compose exec app php bin/console doctrine:migrations:migrate

# Servir l'app en HTTP à la demande (http://localhost:8000)
docker compose exec -d app php -S 0.0.0.0:8000 -t public
```

## Architecture

SaaS multi-tenant de gestion de tournois de football. PHP 8.4 / Symfony, architecture **hexagonale** (DDD), approche TDD. Deux modules (bounded contexts), `Competition` et `Organization`, chacun en trois couches : `Domain/`, `Application/` (use cases) et `Infrastructure/` (adapters). Dépendance à sens unique imposée en CI par `deptrac` : `Competition` peut dépendre d'`Organization`, jamais l'inverse.

- [`docs/architecture.md`](docs/architecture.md) — conventions à suivre par couche (identifiants, exceptions, structure d'un use case, lecture, autorisation, persistance, sécurité, erreurs HTTP, tests). À lire avant d'ajouter un use case ou de toucher une couche.
- [`docs/glossary.md`](docs/glossary.md) — langage métier et termes écartés (`Encounter`, jamais `Match`). À lire avant de nommer un concept.
- [`docs/adr/`](docs/adr/) — le raisonnement de chaque décision structurante (contexte, alternatives rejetées, conséquences), un fichier par décision nommé `NNN-sujet.md` : `ls docs/adr` en donne l'index. Aucun résumé d'ADR n'est recopié ici.
- Ce qui existe (classes, use cases, routes, firewalls) se lit dans le code, `bin/console debug:router` et `config/packages/security.yaml` — jamais recopié dans la documentation.

## Workflow

- **TDD strict, pas test-first** : cycle red-green-refactor, un comportement à la fois. Écrire un test qui échoue pour la bonne raison avant tout code de production, le code minimal pour le faire passer, refactor avant le test suivant. Jamais de test écrit après coup ; jamais plusieurs comportements dans un seul test. Le nombre d'allers-retours peut être allégé sur les étapes triviales, mais le red-before-green n'est jamais sauté.
  - Un seul test à la fois : ne jamais écrire plusieurs méthodes de test dans le même fichier/edit avant d'avoir fait passer la précédente au vert. Si plusieurs comportements sont anticipés, les poser en liste (mentalement ou en commentaire de suivi), pas en code.
  - Après chaque vert, marquer explicitement le passage par l'étape refactor avant d'écrire le prochain test — même quand la réponse est « rien à changer » sur une étape triviale. La pause fait partie de la discipline, pas seulement son résultat.
  - Ce n'est pas une préférence de style : c'est une exigence non négociable du workflow, à appliquer sans qu'il soit nécessaire de le rappeler.
- **Chaque couche teste sa propre API publique, jamais la couche qu'elle délègue** : une règle métier se teste dans la couche qui la porte, une seule fois. `Domain` teste les invariants et règles métier de l'agrégat via son API publique. `Application` ne re-teste jamais une règle métier déjà couverte côté `Domain` — un Handler qui délègue intégralement une règle à l'agrégat (ex: `WithdrawHandler`/`CloseRegistrationHandler` qui appellent `Competition::withdraw()`/`closeRegistration()`) n'a pas à la retester, seulement ce qui lui est propre : orchestration, résolution de dépendances externes (repository qui retourne `null`), tout traitement additionnel que le use case effectue réellement au-delà de la pure délégation. Même principe en cascade pour `Infrastructure`/HTTP : un contrôleur ne re-teste pas les règles déjà couvertes en `Application`, seulement le contrat HTTP (statuts, payloads, routing). Avant d'ajouter un test dans une couche, vérifier si le comportement est déjà couvert par la couche qu'elle délègue (grep/lecture du test correspondant) — si oui, ne pas dupliquer.
- **Tests comportementaux** : vérifier un comportement observable via l'API publique, jamais en miroir de l'implémentation interne. Pas de mock pour vérifier qu'une méthode interne a été appelée. Récupérer les valeurs générées dynamiquement (IDs, etc.) depuis l'API publique plutôt que de les coder en dur — un détail d'implémentation ne doit jamais faire échouer un test.
- **Tests HTTP : arranger les préconditions via repository, jamais en chaînant une requête HTTP de setup** : quand un test de contrôleur a besoin d'un état préexistant (ex: une `Competition` déjà créée avant de tester l'inscription d'une équipe), construire cet état directement via le repository/domaine (`Competition::create()` + `repository->save()`) puis faire un seul `$client->request()` — celui qui teste réellement l'endpoint visé. Chaîner plusieurs appels HTTP dans un même test couple sa réussite à la correction d'un autre contrôleur, et force à désactiver le reboot du kernel entre requêtes (`$client->disableReboot()`) — un garde-fou qui détecte justement les bugs d'état statique/container, à ne pas désactiver pour la requête sous test elle-même.
- **Donnée de test "invalide" jamais prise dans une feature déjà prévue** : pour un test de rejet sur un enum/discriminant fermé (ex: un format de compétition inconnu), vérifier d'abord (`docs/adr/`, issues GitHub ouvertes) que la valeur choisie comme "invalide" ne correspond pas à quelque chose d'explicitement planifié mais pas encore codé. Préférer une valeur délibérément absurde (`not_a_real_format`) à un nom métier plausible qui deviendrait valide un jour — sinon le test se met à échouer pour la mauvaise raison, ou pire, silencieusement, le jour où la feature existe.
- **Design avant implémentation** : pour toute tâche architecturalement significative (nouvel agrégat, nouveau pattern, décision de modélisation DDD ambiguë), valider explicitement l'approche avec l'utilisateur avant le premier `Write`/`Edit`. Pas nécessaire pour les tâches mécaniques (bug fix évident, renommage local). Nuance : un détail d'implémentation mécanique qu'un test en échec révèlera de lui-même (forme exacte d'une interface de repository, emplacement d'un null-check) ne se pré-négocie pas en conversation — laisser le prochain test le faire émerger plutôt que d'enchaîner les questions de cadrage avant d'avoir écrit la moindre ligne.
- **Challenge DDD, pas exécution passive** : le domaine est modélisé en DDD par choix, pas par défaut. Questionner activement le vocabulaire (ubiquitous language), la cohérence d'une règle métier proposée, et l'impact d'une demande sur les invariants du domaine — même quand l'implémentation semble simple à exécuter telle quelle. Signaler un terme sans sens métier ou une règle qui semble incomplète/contradictoire avant d'implémenter, pas après.
- **Confronter une nouvelle décision aux ADR existantes avant d'implémenter** : ne pas résoudre les questions de modélisation une par une, en laissant chaque implémentation faire remonter la question adjacente suivante par ricochet. Avant d'écrire du code, mapper explicitement la décision envisagée contre toutes les ADR déjà actées sur les entités concernées (`docs/adr/`, conventions de `docs/architecture.md`) pour détecter le couplage en amont. Si une nouvelle question remet en cause une décision qui vient d'être prise dans la même conversation, c'est le signal d'arrêter complètement l'implémentation et de faire une seule passe de cadrage sur toutes les questions couplées ouvertes — pas de patcher localement et continuer. Dans ces discussions, formuler une recommandation concrète ancrée dans la vision produit/les ADR existantes plutôt que de se limiter à poser des questions ouvertes — challenger activement en expert métier, pas seulement exécuter la première réponse venue.
- **Critères d'une issue = intention, pas spécification figée** : les critères d'acceptation ou de fin d'une issue sont rédigés avant l'implémentation, sans connaître toutes les options. Si l'implémentation fait émerger une meilleure solution qui s'en écarte, la proposer explicitement (recommandation, pour et contre) plutôt que de s'en tenir à la lettre du ticket. Elle ne s'applique jamais d'office : l'écart se valide d'abord, puis se documente dans la PR, et dans l'ADR si la décision en relève.
- **Loi de Déméter, par jugement pas par réflexe** : ne corriger une chaîne d'appels que si l'objet appelant raisonne sur la structure interne d'un collaborateur à 2+ sauts pour prendre une décision qui devrait appartenir à l'objet le plus proche (ex: comparer une identité en traversant deux relations plutôt que de déléguer la comparaison à l'objet intermédiaire). Une simple lecture via un accesseur qui rend volontairement un agrégat public complet et riche (ex: `getBracket()->countEncounters()`) n'est pas une violation — l'envelopper ajouterait de la duplication d'interface sans gain d'encapsulation réel.
- **Infrastructure : toujours la convention Symfony/Flex standard, jamais une alternative maison pour éviter une dépendance** : si la façon standard nécessite un package (`symfony/dotenv`, `symfony/runtime`, autodiscovery PSR-4 + `exclude`...), l'ajouter plutôt qu'improviser une version "allégée" faite main. S'applique même quand l'incrément est volontairement petit — la petite taille porte sur le périmètre fonctionnel, pas sur le respect des conventions Infra.
- **Anti-énumération ≠ upsert silencieux** : sur un endpoint de création publique keyé par un identifiant naturel (email...), répondre de façon identique que la ressource existe déjà ou non (anti-énumération) ne doit jamais se traduire par l'écrasement de la donnée existante avec les valeurs soumises. Le bon comportement est un no-op protecteur : vérifier l'existence, ne rien écrire si déjà présent, répondre strictement pareil dans les deux cas (voir `RegisterPlayer`/ADR 024 pour l'implémentation de référence).
- **ADR pour les décisions impactantes** : toute décision qui change un contrat, introduit un pattern, ou avait une alternative sérieusement envisagée puis rejetée, est documentée dans `docs/adr/NNN-titre.md` (Contexte / Décision / Conséquences) — pas seulement actée en conversation. Écrire l'ADR fait partie du travail, pas une étape à rattraper plus tard.
- **Documentation strictement professionnelle** : ADR, documentation, instructions agent et messages de commit ne référencent jamais une motivation personnelle, un objectif d'apprentissage ou le contexte conversationnel qui a déclenché une décision — la justification écrite tient sur le seul mérite technique/architectural, comme dans un vrai projet d'entreprise.
- **Petits incréments** : tout travail qui traverse plusieurs couches ou introduit un nouveau pattern se découpe en la plus petite tranche testable possible. Ne concevoir/trancher une étape que lorsque la précédente est terminée — ne pas figer à l'avance des décisions qui ne concernent pas encore l'étape en cours. Si une étape est difficile à committer proprement seule, c'est le signe qu'elle est mal découpée.
- **Itérations approuvées manuellement** : exécuter un incrément, puis s'arrêter et demander explicitement s'il faut continuer, plutôt que d'enchaîner plusieurs incréments sans validation intermédiaire même au sein d'une même session. Chaque itération est un point de reprise propre, y compris entre deux sessions ou deux postes de travail différents.
- **Workflow Git/PR** : `main` est protégée (PR + CI obligatoires, y compris pour le propriétaire du repo — pas de push direct possible). Une branche par sujet, une PR par famille/couche cohérente, commits aussi atomiques que possible à l'intérieur (un par fichier/incrément). Une feature qui traverse plusieurs couches se livre en PR successives, de l'intérieur vers l'extérieur, chacune mergée avant que la suivante ne démarre et laissant `main` verte et sans régression — capacité dormante, jamais cassée ; découpage décidé pendant la passe de cadrage, « Part of #N » sur les PR intermédiaires, « Closes #N » sur la dernière (voir ADR 042). Merge toujours en "Create a merge commit" par défaut (jamais squash, sauf demande explicite ponctuelle) — chaque commit d'incrément reste visible dans l'historique de `main`. Demander confirmation avant de pousser une branche/ouvrir une PR, et avant de merger (le merge se fait souvent depuis l'interface GitHub, pas `gh pr merge`). Après un merge, resynchroniser (`git fetch`/`checkout main`/`pull --ff-only`) puis supprimer la branche locale et distante.
- **`cs-fix` immédiatement après chaque fichier écrit/édité** : lancer `composer cs-fix` sur le fichier juste après l'avoir écrit, avant son `git add`/`commit` — jamais un passage groupé en fin de série de commits, qui force soit un commit cosmétique séparé, soit un `--amend` fourre-tout mélangeant plusieurs incréments.
- **Commits** : format Conventional Commits (`<type>(<scope>): <description>`), toujours avec un corps en français qui explique le pourquoi. Types courants : `feat`, `fix`, `refactor`, `test`, `docs`, `chore`. Un commit par incrément vert — jamais plusieurs incréments regroupés dans un seul commit, jamais d'attente de la fin de session.
- **Documentation : conventions, jamais inventaire** : quand une feature est terminée bout en bout, fermer l'issue GitHub correspondante (ou avancer son statut) dans la foulée — pas en fin de session. `docs/architecture.md`, `docs/glossary.md` et ce fichier ne se mettent à jour que si la feature change une convention, introduit un pattern ou un terme métier — jamais pour inventorier ce qui a été ajouté. Critère : une ligne qui devrait changer à chaque ajout de classe ou de use case n'a pas sa place dans la documentation ; le code, le routeur, `security.yaml` et les ADR le disent déjà, et une copie finit toujours par se périmer. Commit `docs` séparé du/des commit(s) `feat` de la feature elle-même.
- **Réponses en français** : répondre à l'utilisateur en français dans les échanges conversationnels de ce projet (pas seulement dans le code/commits/ADR, déjà en français par convention), sauf s'il bascule lui-même en anglais.

## Suivi de l'avancement

Le suivi des features à venir et de leur statut se fait par **Issues et Milestones GitHub** (`gh issue list`), pas dans ce fichier — voir ADR 037. Une issue "Feature" ne porte que l'intention métier (user story + critères d'acceptation), jamais de détail technique ; la conception émerge à l'implémentation. Statut suivi par labels (`status: needs-definition` → `status: ready` → `status: in-progress`, fermeture = terminé — le label `status:` est retiré à la fermeture, pour qu'une issue close ne remonte plus dans un filtre par statut). Milestones en semver attribués à la livraison, jamais à l'ouverture d'une issue (voir ADR 040) : au merge de la dernière PR d'une feature, création du Milestone MINOR suivant, rattachement de l'issue fermée, tag git et release ; `v1.0.0` = API stabilisée + front livré. La priorité se choisit parmi les issues `status: ready` au moment de démarrer, pas via un numéro de version.

L'historique de ce qui est déjà fait vit dans git log, les issues fermées et `docs/adr/`, pas ici.
